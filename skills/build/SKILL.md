# Build

## What

The implementation command. It picks the next ready issue and drives it through a
disciplined test-first loop. Two branches fold in for the moments you actually hit:
a **bug branch** (a diagnosis loop) when something breaks, and a **`--health`
mode** that runs a quality dashboard.

This is the Lite bundle of `triage`, `tdd`, `diagnose`, and `health` from Standard.

## When

Use `/robobuilder-lite:build` when:
- You have a ready issue and want to implement it properly
- You're doing test-driven development
- Something is broken and you need to debug it methodically → the bug branch
- You want a snapshot of code quality → `/robobuilder-lite:build --health`

## Why

Two failure modes kill implementation quality. First, writing all the tests up front
("horizontal" TDD) produces tests of the *shape* of the code, not its *behavior* —
they pass when things break. Second, debugging by staring at code instead of
building a reliable reproduction wastes hours. Build makes the right path the easy
path: one test → one implementation, and a feedback loop before any hypothesis.

## How

### Stage 1 — Pick

Find the next issue to work on. Issues move through a small state flow:

```
needs-triage → ready → in-progress
```

- Show the issues needing attention (unlabeled, `needs-triage`, or ready), oldest
  first, with a one-line summary each. Let the user pick, or take the issue
  reference they passed as an argument.
- For a bug, **reproduce it first** (see the bug branch) — a confirmed repro makes
  the work far more concrete.
- Any comment you post to the tracker **must** start with:
  `> *This was generated by AI.*`
- Mark the chosen issue in-progress and move on. Don't close or reassign issues
  without the maintainer's say-so.

**DONE when:** one issue is selected, understood, and in-progress.

### Stage 2 — TDD loop

Implement the slice one behavior at a time. **Never write all the tests first.**

**Plan (once):** confirm the public interface with the user, list the behaviors to
test (prioritized — you can't test everything), and look for deep-module
opportunities. Use the project's vocabulary in test and interface names.

**Tracer bullet:** write ONE test for the first behavior → watch it fail (RED) →
write the minimal code to pass (GREEN). This proves the path end to end.

**Incremental loop:** for each remaining behavior:

```
RED:   write the next test  → it fails
GREEN: minimal code to pass  → it passes
```

- One test at a time. Only enough code to pass the current test.
- Test observable behavior through the **public interface**, never private methods
  or internal collaborators. A good test survives an internal refactor.
- Don't anticipate future tests.

**Refactor (only while GREEN):** extract duplication, deepen modules, run tests
after each step. Never refactor while a test is red.

Per-cycle checklist:

```
[ ] Test describes behavior, not implementation
[ ] Test uses the public interface only
[ ] Test would survive an internal refactor
[ ] Code is minimal for this test
[ ] No speculative features added
```

**DONE when:** every prioritized behavior has a passing behavior-driven test and
the code is refactored clean.

### Bug branch — when something breaks

Don't guess. Build a feedback loop first.

1. **Feedback loop (this is the whole skill).** Get a fast, deterministic pass/fail
   signal for the bug: a failing test at the right seam, a curl script, a CLI diff,
   a headless-browser script, a replayed trace. A 2-second deterministic loop is a
   superpower; a 30-second flaky one is barely a loop. For a non-deterministic bug,
   raise the reproduction rate (loop 100×, add stress) until it's debuggable.
2. **Reproduce.** Run the loop; confirm it shows the *user's* failure, not a nearby
   one. Capture the exact symptom.
3. **Hypothesize.** Write 3–5 ranked, **falsifiable** hypotheses ("if X is the
   cause, changing Y makes it disappear") before testing any. Show the list to the
   user — domain knowledge re-ranks it instantly.
4. **Instrument.** One variable at a time. Prefer a debugger/REPL over logs. Tag
   every debug log with a unique prefix like `[DEBUG-a4f2]` so cleanup is one grep.
5. **Fix + regression test.** If a correct seam exists, turn the repro into a
   failing test, watch it fail, fix, watch it pass, re-run the original loop. If no
   correct seam exists, that *is* the finding — flag it for `improve --refactor`.
6. **Cleanup.** Original repro gone, all `[DEBUG-...]` logs removed, the correct
   hypothesis written in the commit message so the next debugger learns.

### `--health` mode — quality dashboard

Run the project's own quality tools and score them. Read-only; never fix anything
here.

1. **Detect the stack.** Read a `## Health Stack` section in CLAUDE.md if present;
   otherwise auto-detect type checker, linter, test runner, dead-code detector, and
   shell linter. Offer to persist the detected stack to CLAUDE.md.
2. **Run each tool** sequentially, capturing exit code, duration, and the last ~50
   lines of output. A missing tool is `SKIPPED`, not a failure.
3. **Score** each category 0–10 and compute a weighted composite
   (tests 28%, type check 22%, lint 18%, dead code 13%, shell 9%; redistribute a
   skipped tool's weight). Present a dashboard table with a composite score and,
   for anything below 7, the actual tool output so the user can act.
4. **Recommend** fixes ranked by `weight × (10 − score)`.

Wrap, don't replace: report exactly what the tools say. Be honest — 100 type errors
with passing tests is not a healthy codebase.

**Next:** run `/robobuilder-lite:improve` before you merge.

## Example

> **User:** build #12 (replay a saved search)
>
> **build (Pick):** #12 is ready and blocked by nothing. Marking in-progress.
>
> **build (TDD):** RED — `test "replaying a saved search restores its filters"`
> fails. GREEN — minimal `SavedSearch#replay` makes it pass. RED — `test "replay
> preserves sort order"`… *(one behavior at a time)*
>
> **build (Bug branch):** replay throws on empty filters. Feedback loop: a failing
> unit test at `SavedSearch#replay`. Hypotheses: 1. nil filters not handled (most
> likely)… Fix + regression test, `[DEBUG-3f]` logs removed.

## Anti-pattern

- **Horizontal TDD.** Writing test1..test5 then impl1..impl5. Produces tests of the
  code's shape, not its behavior. One test → one implementation.
- **Debugging without a loop.** Reading code and guessing. Build the reproduction
  first; the bug is then 90% found.
- **Testing private methods / mocking internal collaborators.** The test breaks on
  every refactor and tells you nothing about behavior.
- **Fixing issues in `--health` mode.** It's a read-only dashboard. Fix separately.
